明日ドローンを飛ばすために飛行計画を通報しようとしたら、DIPS2.0が「メンテナンス中」でサービス停止していました。丸一日たっても再開の見込みは示されていません。気になったので、公開されている調達情報と停止画面のソースコードから、この停止の背景を考えてみました。

## DIPS2.0停止の経過

国土交通省航空局の無人航空機担当のXアカウント（@mlit_mujinki）の投稿を、時系列に並べます。

- 11月25日17時頃：事前の告知なくDIPS2.0がメンテナンスのためサービス停止
- 11月25日21:53：停止から約5時間後に、Xで初めて停止を告知。再開時期は未定（[投稿](https://x.com/mlit_mujinki/status/2125573684891152576)）
- 11月26日17:31：停止の継続を告知。再開までの飛行計画はメールで事後通報するよう案内（[投稿](https://x.com/mlit_mujinki/status/2125869964905296068)）
- 11月26日17:32：メールで通報する15項目を案内（[投稿](https://x.com/mlit_mujinki/status/2125870415147041151)）
- 11月26日21時48分の時点：まだ停止中。航空局のサイトには説明が出ていない

停止から丸一日たって出てきたのが、「メールで事後に通報してください」という案内でした。
これは、近いうちに再開できる見込みが立っていないと言っているのと同じだと私は読んでいます。

ちなみに2025年末のメンテナンスでは、「飛行計画通報機能、飛行許可・承認申請機能、事故等報告機能の利用は可能」として、通報機能を残して運用していました（[航空局 DIPSのお知らせ](https://www.mlit.go.jp/koku/koku_ua_dips.html)）。
今回は通報も含めてすべて止まっています。

## 切り戻せないメンテナンスの可能性

停止の理由や状況についての正式な発表はされていません。
以下は、私の想像です。

緊急停止を伴う「メンテナンス」なので、アプリケーションの変更やバグ対応ではなく、緊急のソフトウェア更新ではないかと思います。その緊急性からして、ここ数日のうちに見つかった脆弱性への対応という可能性が濃厚と考えています。

もちろん、ランサムウェアやシステムへの侵入でサービスを継続できなくなるという最悪のシナリオも考えられなくはありません。国家の航空安全を担う組織が、そう簡単に侵入されたなどと仮定するのは失礼なので、ここは好意的に緊急パッチだと考えておきます。

重大な脆弱性が発見された場合に、緊急パッチのためにサービスを止めること自体は、当然の判断です。

問題はそのあとにあります。

システム変更に際しては、うまくいかなかったときに元の状態へ戻す手順（切り戻し）を必ず用意しておきます。これは運用の常識です。

緊急パッチでも同じです。
サービスを続けることが最優先なのですから、パッチがうまく当たらなければ、ひとまず元の状態に戻して再開し、改めて仕切り直します。
「脆弱性があるから絶対に戻さない」という判断は、よほど深刻な脆弱性でもない限りしません。

パッチを当てるだけなら、普通は数時間で終わります。パッチで問題が出て切り戻しが発生しても、通常は翌日のサービスには間に合わせるよう計画し、体制を組んでいるものです。

しかし、今回は24時間以上たっても再開の見込みが出ていません。パッチに失敗し、切り戻しもできない状態に陥っている可能性が高いと考えています。

いまは復旧の方策を検討している最中で、利用者には「メールで事後に送って」と頼むしかない状況になっているのではないでしょうか。

エンジニアとしては、胃がキリキリとする、なかなか辛い状況です。

## 停止画面のコードから推し量るベンダーの技術力

いまDIPS2.0にアクセスすると「メンテナンス中」としてサービス停止を案内する画面に切り替わっています。おそらくメンテナンスで停止する際は、いつもこのページに切り替えているのだと思います。

<!-- textlint-disable -->

{{< image src="maintenance-page.webp" alt="DIPS2.0の停止画面" />}}

<!-- textlint-enable -->

停止画面には「以下のリンクより各手続きにアクセスすることで手続きいただくことが可能です」とあり、機体登録や飛行計画通報などの手続きサイトへのリンクが並んでいます。
ところが、リンク先もすべて同じ停止画面を返し、手続きはできません。
「各手続きサイトも同時にメンテナンスとなる場合があります」と小さく断り書きはあるものの、メールでの事後通報といった代わりの手段は書かれていません。
停止画面の本文は停止とほぼ同時刻に置き直されていますが、この案内は残ったままです。

DIPS2.0はAWS[^aws]で運用されています。
停止画面の応答はAWSのCDN[^cdn]であるCloudFrontから返され、本文のHTMLはAWSのストレージサービスであるS3に置かれています。
不正なアクセスを遮断するWAF[^waf]も使われており、停止画面はこのWAFが返す独自の応答として表示しているようです。
AWS WAFでは、この独自の応答の本文は4KBまでという上限があります（[AWS WAF quotas](https://docs.aws.amazon.com/waf/latest/developerguide/limits.html)）。

[^aws]: Amazon Web Servicesの略です。

[^cdn]: Content Delivery Networkの略です。

[^waf]: Web Application Firewallの略です。

このページは、骨組みだけのHTMLにJavaScriptで本文を読み込んで表示しています。特に機能もなくアナウンスだけの小さなページですが、コードを見ると気になる点がいくつもありました。

まず、WAFの都合をJavaScriptでごまかしています。

```html
<!-- WAFのアップロード容量の問題（4KBまで）でmainタグは外部HTMLに外だしする -->
<main id="main"></main>
<script type="text/javascript">
  writeHTML('https://www.ossportal.dips.mlit.go.jp/maintenance/portal/maintenance_main_portal.html');
</script>
```

```javascript
// インクルード
function writeHTML(url){
  let req = new XMLHttpRequest();
  req.open('GET', url);
  req.send();
  req.onload = function() {
    if (req.status == 200) {
      document.getElementById('main').innerHTML = req.response;
    }
  }
}
```

WAFの上限に収めるため、本文を別のHTMLに分け、JavaScriptで読み込んでいます。
インフラ側の制約を、ページ側の小細工で吸収した形です。
しかもその事情を説明したコメントが、本番のページにそのまま残って公開されています。

読み込みにはエラー処理がありません。
取得に失敗すると、停止画面なのに本文が空になります。
障害時の画面が、障害に弱い作りというわけです。

次に、テンプレートのプレースホルダーと、コピーしたままの閉じタグのコメントが残っています。

```html
<div class="logo"><img src=".../DRS_Logo.png" alt="サイト名"></div>
```

ロゴの代替テキストが「サイト名」のままです。
テンプレートのプレースホルダーを消し忘れたもので、読み上げソフトでは「サイト名」と読まれます。

```html
<div class="headerBtm">
  ...
</div><!-- /.headerInner -->
```

`headerBtm`の閉じタグに、`/.headerInner`というコメントが付いています。
コピーして貼り付けたあと、直していません。

綴りの誤りもあります。

```html
<p>Please check <a href="...">here</a> for the website of the Civil Aviation Bureau of the Ministry fo Land, Infrastructure, Transport and Tourism.</p>
```

`Ministry fo Land`と、英語版の案内で自分たちの役所の名前を書き損じています。
CSSにも`.modalIdetify`（Identifyのつもりでしょう）というクラス名があります。

作りかけのコードも、そのまま本番に出ています。

```css
/* /.質問アコーディオンの仮作成中 */
```

「仮作成中」のまま、本番で配信されています。

CSSには、変更履歴をコメントで書き込んでいる箇所もあります（個人名は伏せています）。

```css
/* 2021/2/17 〇〇追加 */
main section .statusbar {
  padding: 40px 0px 0px 0px;
}

/* 2021/3/5 〇〇追加 */
.definitionList {
  margin: 0px 40px 40px 30px;
}
```

誰がいつ何を追加したかを、コードのコメントで管理しています。
本来はGitなどのバージョン管理でやることです。
コードに日付と名前を書き込む習慣は、バージョン管理がきちんと使われていないか、使われていても信頼されていない現場で見かけるものです。
こんな習慣は、バージョン管理システム[^vcs]が普及した1990年代に絶滅したと思っていました。
コメントアウトしただけで消していないコードも、あちこちに残っています。

[^vcs]: RCS、CVS、Gitなど、ソースコードの変更履歴を記録し、誰がいつ何を変えたかをたどれるようにする仕組みです。

```css
/*
.environment {
  font-size: 12px;

}
*/
```

書き方も古いままです。

- `<!--[if IE]><meta http-equiv="X-UA-Compatible" content="IE=edge"><![endif]-->`：IEの条件付きコメントはIE10以降では無視される。そもそもIE自体がサポートを終了している
- clearfix、`letter-spacing: -0.4em`でinline-blockの隙間を消すハック、`mgTLL`や`mgT80`のような余白用クラスの大量定義：どれも2010年代前半の書き方

1つずつ見れば小さな問題です。
停止画面が古くさいから停止が長引いた、と言うつもりもありません。

ただ、これは利用者がいちばん目にするタイミングで出るページです。
そこでさえ、次のような状態にあります。

- プレースホルダーの消し忘れ
- 綴りの誤り
- 「仮作成中」のコメント
- インフラの事情を説明したコメント
- コードに書き込んだ変更履歴

どれも、レビューを通っていればすぐに指摘される種類のものです。
見えるところでこの程度なら、見えないところの変更管理や作業手順がどうなっているかは想像がつきます。
今回の停止が長引いているのも、この延長線上にあるように見えます。

## まとめ

そもそもDIPS2.0は、インターフェイスが一般的なUXとはほど遠く、背景にあるプロセスや機能間の関係を画面から読み取りづらい、使いづらいシステムです。

通報しようとしたらそのシステムが長期間止まっていたので、ちょっと恨みがましくなってしまいました。

しかし、公開されているサービスのコードはユーザーには見えていますから、その品質には気をつけてほしいものです。コーディングするだけでなく、インスペクションやコードレビューが行われていれば潰せる程度の問題ばかりです。しかもこれらの検査の大半を20年近く前からツールで自動化できます。ましてや、生成AIが開発に入ってきたこの数年であれば、AIがこれらのツールを回してくれます。

日本に典型的なSIerさんのレベルだと思いますが、大丈夫なのでしょうか。

 
明日の飛行は、メールで事後通報することになりそうです。

## 11月28日追記：一部の手続きの再開

11月28日現在、DIPS2.0にはログインできるようになっています。

DIPS2.0のお知らせ欄（11月27日19時30分更新）によると、11月27日19時の時点で、飛行許可・承認申請、飛行計画の通報・確認、事故等の報告は使えるようになりました。
一方で、無人航空機の登録申請、技能証明の取得申請、機体認証の取得申請は引き続き使えません。
お知らせ欄では、今回の停止を「臨時メンテナンス」と呼んでいます。

止まったままの手続きについては、次の扱いが示されています。

- 機体登録：停止の影響で更新できないまま有効期限が切れる機体は、航空法施行規則第236条の8第2項の「天災その他やむを得ない事由」に当たるとして、登録の有効期間を延ばす。延長後の満了日は改めて告知
- 技能証明：停止の影響で申請期間中の手続きができなかった人は、本来の期間内の申請とみなす予定。詳細は改めて告知

また、11月30日15時頃から22時50分頃に予定していたDIPS2.0全機能のメンテナンスは、11月27日20時45分の更新で延期になりました。
新しい日程は決まり次第、お知らせ欄で告知するとしています。
