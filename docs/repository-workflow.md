# リポジトリ運用ルール

**制定日**: 2026-11-25
**関連ADR**: `docs/architectural-decision.md` ADR-0007

記事の執筆・変更と公開の手順を定める。GitHub Flow に従い、
`main` への変更はすべてプルリクエスト（PR）のマージで行う。
Mac での手作業、Mac 上の Claude Code セッション、
Issue の依頼から自動で作る下書きのいずれにも同じルールを適用する。

## 基本ルール

- `main` は保護する。デフォルトブランチは `main` のまま変えない
- 記事の追加・変更は、必ずブランチを切って PR を出す。誤字修正も例外としない
- 公開は PR を `main` にマージすることで行う
- `main` への直接 push は禁止する。Ruleset のバイパス対象には誰も登録しない
- 管理者は Ruleset そのものを無効にできてしまうが、無効にして作業することは禁止する。
  緊急時も、修正の PR を作ってすぐマージする

## 作業の流れ

1. 作業を始める前に、現在のブランチを確認する
2. `main` にいる場合は、作業用のブランチを切る
   - 記事: `content/<記事のスラッグ>`
   - 設定・テンプレートの変更: `feature/<名前>`、`fix/<名前>`、`refactor/<名前>`
3. 既存のブランチ（自動で作った下書きなど）を仕上げる場合は、
   そのブランチに切り替えて作業し、新しいブランチは切らない
4. コミットしてブランチを push し、PR を作る。PR のタイトルは「PR のタイトル」の節に従う
5. PR の検査が通ったら、squash merge する。マージで `main` が更新され、公開される
6. マージが成功したら、ローカルでも `main` を最新にして戻り、マージしたブランチは残さない。
   マージが失敗したときは、ブランチを削除しない。
   リモートの作業ブランチは、マージ時に GitHub が自動で削除する
   1. `gh pr merge --squash --delete-branch` でマージする。gh はマージが成功したときだけ、
      `main` に切り替えてローカルの作業ブランチを削除する。
      GitHub の画面でマージした場合は、この手順を飛ばす
   2. `git switch main` で `main` に戻る
   3. `git pull` で `main` を最新にする
   4. ローカルの作業ブランチが残っていたら、PR が merged になっていることを確かめてから
      `git branch -D` で削除する。squash merge したブランチは、
      `git branch -d` では未マージと判定されて削除できない

## 検査

検査はすべて PR で行い、通らなければマージできない。
commit や push の時点では検査しない。

ブランチでは書きかけの状態で commit や push をするのが普通であり、
公開されるのはマージの時点だからである。
自動で作る下書きを途中で止めないためでもある。
このため、husky による commit 時と push 時の hook は使わない。

| ワークフロー | 内容 |
|------|------|
| `textlint.yml` | 記事全体を textlint で検査する。PR を作った人や push した人が誰でも検査する |
| `ogp-check.yml` | `content/blog/` のすべての記事に `ogp.webp` があり、frontmatter に `social_media_card = "ogp.webp"` があるかを確かめる |

検査の対象は、PR で変更した記事に絞らない。
すべての記事に OGP 画像があることが要件であり、全記事を調べても数秒で終わるためである。
`content/projects/` のページは `cover.webp` を OGP 画像に使うので、対象外とする。
`ogp.webp` が今のタイトルとタグで作られているかは検査しない。

## マージ方式

squash merge のみを使う。merge commit と rebase merge は、リポジトリの設定で無効にする。

`bluesky-post.yml` は `git diff --name-status HEAD~1 HEAD` で新規記事を検出する。
rebase merge では PR のコミットが1つずつ `main` に並び、
`HEAD~1` との差分には最後のコミットの変更しか含まれない。
そのため、それより前のコミットで追加された記事が検出から漏れる。
squash merge なら PR 全体が1コミットになり、この問題が起きない。

squash merge のコミットのタイトルには PR のタイトルを、本文には PR の説明を使うよう、
リポジトリの設定を変える。既定の設定では、PR のコミットが1つだけのときに
そのコミットの件名がタイトルになり、本文には全コミットのメッセージが並ぶ。

## PR のタイトル

squash merge では PR のタイトルが `main` のコミットのタイトルになるため、
PR のタイトルの先頭に次の接頭辞を付ける。オーナーが作る PR にも、Claude が作る PR にも適用する。

| 接頭辞 | 使う場面 |
|------|------|
| `content:` | 記事の追加・更新・修正。誤字、タグ、メタデータ、記事内の画像も含む |
| `feat:` | サイトの機能の追加・変更。テンプレート、コンポーネント、スクリプト、ワークフロー |
| `fix:` | サイトの機能の不具合の修正 |
| `style:` | 見た目だけの変更。CSS、フォント、レイアウト、サイト共通の画像 |
| `refactor:` | 動作を変えない構造の整理 |
| `perf:` | 表示速度やファイルサイズの改善 |
| `docs:` | リポジトリの文書。`docs/`、README、CLAUDE.md |
| `chore:` | 上のどれにも当たらない保守。依存の更新、テーマの更新、不要なファイルの削除 |

- 記事だけの変更には、必ず `content:` を使う。記事の誤りを直す場合も `fix:` にはしない
- 記事とそれ以外を一緒に変えた場合は、主な目的で選ぶ
- 互換性のない変更には `!` を付ける（例: `refactor!:`）
- 接頭辞に続く件名は英語で書き、小文字で始める。末尾にピリオドを付けない
  （例: `content: add Raspberry Pi 4 home server article`）

ブランチ上のコミットメッセージは `main` に残らないため、接頭辞のルールは定めない。
Claude の commit スキルの設定（`.claude/simple-commit.local.md`）は、この表と同じ接頭辞を使う。

## リポジトリの設定

GitHub の Ruleset で `main` に次の制約をかける。

| 項目 | 設定 |
|------|------|
| 対象 | `main` ブランチ |
| マージ前の PR | 必須 |
| 必要な承認数 | 0 |
| 必須のステータスチェック | `textlint.yml`、`ogp-check.yml` |
| バイパスを許可する人 | なし（管理者も含む） |
| force push | 禁止 |
| ブランチの削除 | 禁止 |

承認数を 0 にするのは、GitHub では自分の PR を自分で承認できないためである。
1 以上にすると、書き手が1人のこのリポジトリではマージできなくなる。

タグは Ruleset の対象外なので、`/blog-release` のタグ push はそのまま行える。

リポジトリ全体の設定は次のとおりにする。

| 項目 | 設定 |
|------|------|
| 許可するマージ方式 | squash merge のみ |
| squash merge のコミットのタイトル | PR のタイトル（`PR_TITLE`） |
| squash merge のコミットの本文 | PR の説明（`PR_BODY`） |
| マージ後の作業ブランチ | 自動で削除する |

## PR とマージで動くワークフロー

PR の作成時と、PR への push のたびに、次のワークフローが動く。

| ワークフロー | 内容 |
|------|------|
| `textlint.yml` | 記事を textlint で検査する（必須） |
| `ogp-check.yml` | 全記事の `ogp.webp` と `social_media_card` を確かめる（必須） |
| `claude-code-review.yml` | Claude Code が PR をレビューする |

`claude-code-review.yml` は Claude のサブスクリプションの利用枠を使う。
すべての変更が PR を通るようになるので、残すかどうかは未決定である。

PR のマージは `main` への push として扱われ、次のワークフローが動く。

| ワークフロー | 内容 |
|------|------|
| `deploy.yml` | Zola でビルドし、Cloudflare Workers にデプロイする |
| `bluesky-post.yml` | 新規記事があれば Bluesky に投稿する |

## Issue による執筆依頼

将来、GitHub Issue に書いた依頼をもとに下書きを自動で作る。
実行環境は Raspberry Pi か GitHub Actions（`claude-code-action`）のどちらかで、まだ決めていない。
どちらで作る場合も、このリポジトリの取り決めとして次を定める。

- 処理するのは、オーナー自身が立て、かつ `article-request` ラベルが付いた open の Issue だけとする
- 読むのは Issue の本文だけとし、コメントは読まない
- このリポジトリは public で、第三者も Issue を立てられる。
  一方、ラベルを付けられるのは triage 以上の権限を持つ人だけである。
  作成者とラベルの両方を条件にすることで、第三者が書いた文章が依頼として扱われることを防ぐ
- Issue テンプレート（Issue Forms の `labels:`）でこのラベルを自動で付けない。
  自動で付けると、第三者が立てた Issue にも付いてしまう
- `article-request` の Issue に `@claude` を書かない。
  `claude.yml` は Issue の本文に `@claude` があると動くので、同じ依頼が二重に処理される
- 自動で作った下書きは、そのまま公開できる品質ではない。
  Mac で仕上げてから PR をマージする

ラベルの作成は、この自動化を作るときに行う。
実行環境のほか、認証方式、下書きのコミットの author 名、PR を自動で作るかどうかも未決定である。
